### 修正后的 FSD + Vue 3 结论

**1. 依赖铁律（隔离层）**
`App.vue` 仅作为全局 Provider（主题/错误边界）和 `RouterView` 容器，**严禁**导入任何业务 Widget。依赖链必须是单向的：`Page（页面） -> Widget（部件）`，方向绝不可逆。

**2. Widget 的本质（哑组件）**
Widget 不是“全局外壳”，而是**可复用的纯交互单元**。它必须通过 `props` 和 `slots` 接收外部差异（数据与样式变体），严禁内部直接引用路由或全局 Store 获取数据。数据源（API/Store）统一由 Page 层注入。

**3. 路由状态的组合策略**
不将 Widget 放入 `App.vue` 是绝对正确的标准做法。不同路由的状态差异，通过不同的 Page 组合不同的 Widget 来实现；严禁在 App 层使用全局 `if/else` 或状态开关去控制业务模块的显隐。

**4. 缓存策略的关键修正（针对重型组件）**

- **App 级缓存（仅限 UI 记忆）**：可在 `RouterView` 外层使用 `KeepAlive`（配合 `include` 白名单），但**仅限**用于记忆页面级的轻量 UI 状态（如滚动条、Tab 切换），不承担数据持久化职责。
- **重型组件优化（下沉策略）**：绝对不要将重型图表或复杂编辑器挂在 App 级的 `KeepAlive` 中。正确做法是**下沉到页面内部**，对特定的重型 Widget 进行局部 `KeepAlive` 包裹，或使用 `v-memo` 进行精细化缓存，避免拖垮全局路由切换性能。
- **动态路由防呆**：若缓存页面依赖动态参数（如 `/detail/:id` ），必须在该 Page 组件的 `onActivated` 钩子中监听 `id` 变化，强制刷新核心数据，防止参数变了但页面数据依然陈旧的 Bug。

**5. 长生命周期状态的归宿**
如果需要在路由跳转后完整保留多步骤表单等重型业务状态，**绝不依赖**浏览器的 DOM 缓存（内存不可控），必须将该状态提升至 `Pinia / Store` 中管理，由 Store 配合页面生命周期进行数据的持久化与恢复。
